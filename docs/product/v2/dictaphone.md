# ИИ-диктофон

[Вторая версия](index.md), витрина этого репозитория: та же дверь для людей, что и у чата, и ничего в ней не переписывает — см. [о сервисе](../about.md) и [две аудитории](../audiences.md).

**Состояние: в плане.** В коде из перечисленного ниже нет ничего.

## Цель

Дать человеку записать разговор — встречу, лекцию, конференцию — и тут же спрашивать по нему, не переключаясь на другой экран и не пересказывая содержание руками.

Что для этого нужно:

- **Записать** звук с микрофона в браузере, до получаса, без потери хвоста при остановке.
- **Расшифровать** речь: черновой текст виден по ходу записи, точный — после остановки.
- **Показать расшифровку** там, где её видно и можно поправить руками: в заметке диалога.
- **Ответить на вопросы** по записи в обычном чате — той же моделью, теми же инструментами, теми же
  навыками, что и везде. Отличие ровно одно: пока идёт запись, заметка обновляется сама, поэтому
  модель всегда видит свежий текст.
- **Сохранить звук** так, чтобы его можно было переслушать, и так, чтобы он не лежал в открытом
  доступе.

## Как это работает

```
запись → getUserMedia → MediaRecorder (чанки по 1 с) → сегмент каждые 20 с
      → POST /api/dictaphone/transcribe (Whisper) → текст в левую панель по номеру сегмента
      → первый сегмент создаёт диалог, каждый следующий переписывает его заметку
         → чат справа читает заметку обычным инструментом read_chat_note
стоп  → хвост дописывается в очередь → точный текст заменяет черновик
      → POST /api/dictaphone/recordings (транскрипт и метаданные в БД)
      → POST /api/dictaphone/recordings/{id}/audio (звук в приватный бакет)
```

Порядок «сначала текст, потом звук» намеренный: если загрузка аудио упадёт, расшифровка и заметка
уже целы.

Четыре вещи, которые ломают наивную реализацию и потому заложены в код и в тесты:

- У **webm только первый чанк** содержит заголовок контейнера. Остальные — отдельные кластеры, сами
  по себе не декодируются. Каждый сегмент собирается как «заголовок + своя часть».
- Сегменты **склеиваются по номеру**, а не по порядку ответов: сеть переставляет ответы.
- **Хвост при остановке** не выбрасывается никогда; ждём распознавания последнего сегмента.
- **Тип файла не угадываем**: iOS Safari пишет `audio/mp4`, сервер приводит его к формату, который
  понимает провайдер.

## Сосед по технике

У диктофона есть сосед — [голосовой чат](voice.md). Общего у них ровно столько, сколько стоит делать
один раз: разрешение на микрофон, коды ошибок, распознавание речи на сервере, суточные минуты.
Дальше дороги расходятся: диктофон пишет встречу и расшифровывает её целиком, голосовой чат — короткий
разговор с моделью. Это две разные работы, а не переключатель.

## Критерии готовности

- [ ] Запись до 30 минут с микрофона; остановка не теряет хвост
- [ ] Живая расшифровка идёт по ходу записи (проверено в Chrome и на Android)
- [ ] После остановки точный текст заменяет черновик; при сбое распознавания черновик остаётся
- [ ] Диалог создаётся сам, заметка обновляется по ходу записи
- [ ] Вопрос по записи в чате: модель отвечает по содержанию, а не по догадке
- [ ] Чат в диктофоне = обычный чат: та же модель, навыки, инструменты, шаринг, заметка
- [ ] Звук играется с перемоткой, доступен только владельцу
- [ ] Удаление диалога удаляет звук из хранилища
- [ ] Дневные лимиты минут работают; подделать длительность в запросе нельзя
- [ ] Firefox — без превью, но запись и расшифровка работают; iOS Safari — `audio/mp4`
- [ ] `make test-coverage`, `npm run test`, `make lint`, `make docs-build` — зелёные
- [ ] `/privacy` честно перечисляет, куда уходит звук

## Не входит

- **Диаризация** (кто что сказал) — отложена, но заложена: храним звук и границы сегментов, поэтому
  повторный прогон позже не потребует перезаписи встречи. Отдельный пункт, отдельные деньги.
- **Веб-поиск** в чате — [отдельная тула](websearch.md), отдельный план. В диктофоне он появится сам:
  справа работает тот же `/api/chat`.
- **Биллинг** — как у картинок, только суточные лимиты и лог стоимости. Полный баланс —
  [отдельная работа](billing.md).
- **Редактирование расшифровки** в интерфейсе, экспорт в другие форматы, хранение звука дольше
  диалога, корпоративный контур: компаниям — [LibreChat](librechat.md), другой деплой.
- **Отдельная политика хранения звука** — вместе с диалогом и не дольше: удалили чат — удалился звук.
  Отдельный срок и автоудаление по возрасту — только если появится запрос, а не «на всякий случай».

## Риски

1. **Предел размера запроса на хостинге.** Перед приложением стоит веб-сервер, который может
   отвергнуть загрузку раньше, чем она дойдёт до кода. Проверяется первым делом; если не проходит —
   потолок записи падает с получаса до считанных минут.
2. **Android делит микрофон** между записью и живым распознаванием: запись может получиться тихой.
   Проверять на живом телефоне, а не только в эмуляторе.
3. **Приватность.** Звук уходит третьим сторонам: распознавание в браузере — в Google, точная
   расшифровка — в OpenRouter, хранение — в Cloud.ru. Отсюда честный текст на `/privacy` и
   рубильник, выключающий живое превью.
4. **Утечка денег.** Биллинга нет, счёт у OpenRouter предоплаченный, поэтому общий суточный потолок
   на инстанс обязателен до включения на проде.
5. **Сборка без второй точки входа** удалит на проде файлы диктофона, пока чат будет жив: `plan_sync`
   в деплое убирает то, чего нет в локальной сборке.
6. **Ссылка `/chat?c=<id>`** трогает ядро чата. Если правка окажется рискованной — есть запасной
   путь без вмешательства в поведение нового чата.
